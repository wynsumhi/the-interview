# RAG Test README

## 한 장면으로 설명하면

이 테스트의 RAG는 "면접 질문을 잘 맞히는 시스템"보다는 "지난 인터뷰의 결을 다시 꺼내 읽는 편집부 아카이브"에 가깝습니다.
지금 들어온 질문과 답변을 하나의 인터뷰 장면으로 보고, 이전 대화 기록 중 분위기와 주제가 닮은 장면을 찾아 다시 붙여 주는 흐름입니다.

예를 들어, 이번 답변이 새 앨범의 분위기나 무대 직전의 감각을 다루고 있다면 시스템은 과거 인터뷰 기록 중 비슷한 문답을 찾아
"이 사람은 예전에 이런 맥락에서 이렇게 말했다"는 식의 참고 문맥을 LLM 앞에 놓아 줍니다.

## 이 테스트가 검증하는 것

`ai/tests/rag`는 인터뷰형 Q&A 데이터를 대상으로 아주 작은 RAG 파이프라인을 실험하는 테스트 공간입니다.
다만 톤은 채용 면접 대비보다 매거진 인터뷰에 더 가깝습니다. 핵심은 정답 여부보다도, 지금의 답변에 어울리는
이전 인터뷰 장면을 얼마나 자연스럽게 다시 불러올 수 있느냐입니다.

검증 범위는 아래 네 가지입니다.

- 인터뷰의 한 턴을 질문과 답변이 함께 있는 하나의 문서로 다룰 수 있는지
- 현재 질문과 답변을 묶어 검색 질의로 만들 수 있는지
- Qdrant에서 의미적으로 가까운 이전 인터뷰 턴을 찾을 수 있는지
- 검색 결과를 LLM이 바로 참고할 수 있는 읽기 쉬운 컨텍스트로 바꿀 수 있는지

## 동작 방식

### 1. 인터뷰 턴을 그대로 보관합니다

이 테스트는 문서를 잘게 자르지 않습니다.
한 번의 질문과 한 번의 답변을 하나의 완결된 장면으로 보고 그대로 저장합니다.

`InterviewTurn`에는 아래 정보가 들어갑니다.

- `session_id`
- `question`
- `answer`
- `turn_index`
- `metadata`

이 값들은 `build_turn_document()`에서 하나의 텍스트로 합쳐지고, 그 텍스트가 임베딩 입력이 됩니다.

### 2. 임베딩은 Qwen3 형식을 사용합니다

`qwen3_embedding.py`는 OpenAI 호환 `/embeddings` API 형식으로 요청을 보내는 클라이언트입니다.
테스트에서는 실제 서버 대신 stub 또는 mock transport를 사용해 요청 형식과 응답 정렬 방식을 검증합니다.

즉, 이 디렉터리는 "어떤 모델이 가장 좋은가"를 비교하기보다
"임베딩 요청을 안정적으로 만들고, 받은 벡터를 RAG 흐름에 연결할 수 있는가"를 확인합니다.

### 3. 검색은 메모리 기반 Qdrant로 끝냅니다

`qdrant_store.py`는 `QdrantClient(location=":memory:")`를 사용합니다.
별도 서버를 띄우지 않고도 컬렉션 생성, upsert, search, count 흐름을 바로 검증할 수 있게 한 구성입니다.

포인트 ID는 문자열 그대로 쓰지 않고 숫자 ID로 변환해 저장하고,
원래 ID는 payload 안의 `external_point_id`로 함께 보관합니다.
그래서 검색 결과를 다시 읽을 때는 사람이 이해하기 쉬운 원래 인터뷰 턴 ID를 그대로 복원할 수 있습니다.

### 4. 검색 결과는 LLM이 읽기 좋은 인터뷰 메모로 정리합니다

`format_retrieved_turns_for_llm()`은 검색된 이전 문답을 점수, 세션 ID, 턴 번호, 질문, 답변, 메타데이터와 함께 정리합니다.
형식상 프롬프트 컨텍스트이지만, 읽는 감각은 "이전 호 인터뷰에서 비슷한 이야기가 나온 대목"에 가깝습니다.

## 왜 청크를 자르지 않았는가

이 테스트의 기본 설정은 아래와 같습니다.

- `top_k=3`
- `score_threshold=0.35`
- `chunk_size=None`
- `chunk_overlap=0`
- `rerank_enabled=False`

여기서 중요한 건 `chunk_size=None`과 `rerank_enabled=False`입니다.

매거진 인터뷰 문맥에서는 질문과 답변이 붙어 있어야 의미가 살아납니다.
질문만 따로, 답변만 따로 쪼개면 말의 결이나 의도가 쉽게 흐려집니다.
그래서 이 실험은 "문답 한 턴"을 최소 검색 단위로 보고, 우선은 그 장면 자체를 그대로 되살리는 쪽을 택했습니다.

리랭크도 같은 이유로 꺼 두었습니다.
현재 단계에서는 복잡한 후처리보다, 임베딩과 벡터 검색만으로도 비슷한 인터뷰 장면을 얼마나 안정적으로 찾는지 보는 것이 목적입니다.

## 샘플 데이터의 읽는 법

`sample_interview_data.py`에는 앨범 작업, 무대 감각, 협업의 리듬, 혼자 있는 시간의 루틴처럼
매거진 인터뷰에서 나올 법한 서로 다른 결의 인터뷰 턴이 들어 있습니다.
이 샘플은 "지금의 장면과 닮은 이전 장면을 잘 불러오는가"를 보기 위한 작은 편집본입니다.

예를 들어 현재 입력이 앨범의 정서와 무대 직전의 감각을 함께 건드리면,
검색 결과 상단에는 `session-album-001`, `session-stage-001` 같은 장면이 우선적으로 올라와야 합니다.
반대로 협업 방식이나 아침 루틴에 가까운 질문이라면 다른 턴이 더 가까운 후보가 됩니다.

## 샘플 RAG 실행 결과

테스트 통과 여부와 별개로, 샘플 인터뷰 데이터를 실제로 색인한 뒤 아래 입력으로 검색을 수행했습니다.

### 입력

질문:
`무대에 오르기 직전, 앨범의 감정은 어떻게 다시 살아났나요?`

답변:
`밤의 공기와 첫 박자의 떨림이 무대의 감정을 다시 또렷하게 만들어 줬습니다.`

### 검색 결과

```text
session-album-001-1    session-album-001    0.8165
session-stage-001-2    session-stage-001    0.5774
```

현재 입력이 밤의 공기, 앨범의 정서, 첫 박자의 무대 감각을 함께 건드리고 있어서,
협업이나 루틴 장면보다 앨범과 무대 관련 인터뷰 장면이 먼저 검색되는 것을 확인할 수 있습니다.

### LLM에 넘기는 컨텍스트 예시

```text
[유사도 0.8165]
포인트 ID: session-album-001-1
세션 ID: session-album-001
턴 순번: 1
이전 질문: 새 앨범을 만들 때 가장 오래 붙들고 있던 감정은 무엇이었나요?
이전 답변: 이번 앨범은 밤의 공기와 혼자 남겨진 시간을 오래 바라보며 만들었어요. 조용한 장면이지만 마음속에서는 가장 큰 파도가 치고 있었죠.
메타데이터: mood=night, topic=album

[유사도 0.5774]
포인트 ID: session-stage-001-2
세션 ID: session-stage-001
턴 순번: 2
이전 질문: 무대에 오르기 직전에는 어떤 풍경을 가장 먼저 떠올리나요?
이전 답변: 관객의 표정보다 먼저 조명 냄새와 첫 박자의 진동을 떠올려요. 무대는 늘 긴장되지만, 그 떨림이 저를 가장 또렷하게 만들어 줍니다.
메타데이터: focus=performance, topic=stage
```

이 예시는 이 디렉터리의 RAG가 "정답을 찾는 검색기"라기보다, 현재 문답과 결이 비슷한 이전 인터뷰 장면을 다시 붙여 주는 구조라는 점을 잘 보여 줍니다.

## 코드가 작동하는 흐름

이 디렉터리의 코드는 아래 순서로 이어집니다.

1. `sample_interview_data.py` 또는 테스트 안의 샘플 문답으로 `InterviewTurn` 데이터를 만듭니다.
2. `interview_rag.py`의 `build_turn_document()`가 질문과 답변을 한 문서로 묶습니다.
3. `qwen3_embedding.py` 또는 테스트용 stub이 그 문서를 벡터로 바꿉니다.
4. `qdrant_store.py`가 벡터와 payload를 메모리 기반 Qdrant에 저장합니다.
5. 새 질문과 답변이 들어오면 `build_query_text()`가 현재 턴을 검색용 질의로 만듭니다.
6. `InterviewRAGIndex.retrieve_similar_turns()`가 유사한 이전 인터뷰 턴을 검색합니다.
7. `format_retrieved_turns_for_llm()`이 검색 결과를 LLM이 읽기 쉬운 컨텍스트 문자열로 정리합니다.

## RAG 기능 범위

현재 인터뷰 히스토리 기반 RAG는 사용자의 과거 답변 맥락을 다시 불러와,
더 자연스럽고 연속성 있는 인터뷰 경험을 만드는 것을 목표로 합니다.
우선순위는 실제 서비스 흐름에 바로 필요한 기능부터 두고,
이후 품질 개선과 운영 편의 기능으로 확장하는 방식이 적절합니다.

### Must

- 인터뷰 종료 시 히스토리 기반 RAG 업데이트
  인터뷰가 종료되면 해당 세션의 질문과 답변을 사용자 히스토리로 저장하고, RAG 인덱스를 즉시 업데이트합니다.
- 꼬리질문 생성 시 히스토리 참조
  현재 질문과 사용자의 답변을 기준으로 과거 유사 인터뷰 기록을 검색하고, 이를 꼬리질문 생성의 참고 문맥으로 활용합니다.
- 인터뷰 히스토리 삭제 시 RAG 동기화
  사용자가 인터뷰 기록을 삭제하면 RAG 인덱스에서도 해당 기록이 함께 제거되어야 합니다.
- 사용자별 히스토리 격리
  RAG 검색은 반드시 사용자 단위로 분리되어야 하며, 다른 사용자의 인터뷰 기록이 검색 결과에 포함되어서는 안 됩니다.
- 기본 검색 정책 적용
  `top_k`, score threshold, 사용자 필터 등 최소한의 검색 규칙을 정의해 일관된 검색 품질을 유지합니다.

### Should

- 품질이 낮은 답변 필터링
  너무 짧은 답변, 무의미한 응답, 중복된 기록은 인덱싱 대상에서 제외하거나 우선순위를 낮춥니다.
- 카테고리 기반 검색 범위 조정
  직무, 주제, 인터뷰 유형 등 메타데이터를 기준으로 검색 범위를 좁혀 더 적절한 과거 기록을 참조할 수 있도록 합니다.
- 최신성 반영
  오래된 히스토리보다 최근 인터뷰 기록을 더 우선적으로 참고하도록 가중치를 둘 수 있습니다.
- 검색 결과 로그 저장
  어떤 히스토리가 검색되었고, 어떤 꼬리질문 생성에 사용되었는지 기록해 디버깅과 품질 개선에 활용합니다.

### Later

- 답변 일관성 점검
  현재 답변과 과거 답변 사이의 차이나 충돌을 감지해, 확인형 꼬리질문이나 심화 질문 생성에 활용할 수 있습니다.
- 요약형 컨텍스트 생성
  검색된 과거 답변 원문을 그대로 사용하는 대신, 핵심 맥락만 요약해 LLM 입력으로 제공하는 방식을 도입할 수 있습니다.
- 추천 질문 확장
  꼬리질문뿐 아니라, 사용자의 반복적으로 드러나는 강점이나 경험을 기반으로 심화 질문이나 예상 질문 추천으로 확장할 수 있습니다.
- 전체 재색인 기능
  임베딩 모델 변경, 메타데이터 스키마 변경, 장애 복구 상황에 대비해 전체 히스토리를 재색인하는 기능을 마련할 수 있습니다.
- 운영자용 조회 기능
  특정 사용자의 RAG 상태, 최근 검색 결과, 동기화 여부 등을 확인할 수 있는 운영 도구를 제공할 수 있습니다.

## FastAPI에 붙일 RAG API

현재 `ai/app`의 FastAPI는 `/api/v1/ai/interview` 아래에서
인터뷰 시작 질문 생성, 다음 회차 시작 질문 생성, 타이틀 생성, 음성 기반 파이프라인 실행을 맡고 있습니다.
향후 STT가 분리되어 백엔드가 음성이 아니라 텍스트를 AI 서버에 전달하더라도,
꼬리질문 생성 책임이 AI 서버에 있다면 RAG 검색은 외부 API가 아니라 AI 서버 내부 단계로 처리하는 편이 더 자연스럽습니다.

즉, 현재 구조에서는 "검색 API를 따로 열어 두는 방식"보다
"기존 `/interview/pipeline`이 내부에서 RAG 검색까지 수행하도록 확장하는 방식"이 더 단순하고 일관됩니다.

가장 먼저 필요한 API는 아래 3개입니다.

### 1. 인터뷰 종료 후 히스토리 적재

- `POST /api/v1/ai/interview/rag/index`
- 목적: 인터뷰 종료 시 해당 세션의 질문/답변을 사용자 히스토리 RAG에 적재합니다.
- 요청 예시 필드:
  `user_id`, `interview_id`, `session_id`, `turns`, `metadata`
- 응답 예시 필드:
  `indexed_count`, `collection_name`, `status`

이 API는 백엔드가 인터뷰 종료 시점에 호출하면 됩니다.
한 세션 전체를 한 번에 넘겨도 되고, 질문/답변 턴 배열 형태로 넘겨도 됩니다.

### 2. 인터뷰 히스토리 삭제 반영

- `DELETE /api/v1/ai/interview/rag/index/{history_id}`
- 목적: 사용자가 삭제한 인터뷰 기록을 RAG 인덱스에서도 제거합니다.
- 경로 또는 요청 필드:
  `history_id`
- 추가 필드:
  `user_id`
- 응답 예시 필드:
  `deleted_count`, `status`

삭제 API는 백엔드의 인터뷰 삭제 로직과 반드시 같은 트랜잭션 흐름 또는 같은 이벤트 체인 안에서 호출되어야 합니다.
그래야 DB와 RAG 인덱스가 서로 다른 상태로 남지 않습니다.

### 3. 기존 인터뷰 파이프라인 확장

- `POST /api/v1/ai/interview/pipeline`
- 목적: 사용자 입력이 들어오면 AI 서버 내부에서 RAG 검색, 꼬리질문 생성, TTS까지 한 번에 처리합니다.
- 현재:
  음성 업로드 기반 STT + 질문 생성 + TTS
- 확장 후:
  텍스트 입력 또는 음성 입력을 받아 내부적으로 사용자 히스토리 검색 + 꼬리질문 생성 + TTS 수행

여기서 중요한 점은 RAG 검색이 외부 API로 노출되지 않는다는 것입니다.
AI 서버는 `pipeline` 요청을 받으면 내부적으로 사용자 히스토리를 검색하고,
검색 결과를 프롬프트 문맥에 넣은 뒤 꼬리질문을 생성합니다.
TTS까지 AI 서버가 담당한다면 질문 텍스트와 오디오를 함께 반환하면 됩니다.

STT가 별도 서비스로 분리된 이후에는,
기존 `/interview/pipeline`이 multipart 음성 업로드만 받는 구조에서
텍스트 기반 요청도 함께 받을 수 있도록 확장하는 방향이 가장 자연스럽습니다.

## 있으면 좋은 추가 API

### 재색인 API

- `POST /api/v1/ai/interview/rag/reindex`
- 목적: 임베딩 모델 변경, 메타데이터 구조 변경, 장애 복구 시 전체 또는 사용자 단위 재색인을 수행합니다.

이 API는 운영용에 가깝기 때문에 초기에는 없어도 되지만,
실서비스 단계에서는 결국 필요해질 가능성이 높습니다.

### 디버그 조회 API

- `GET /api/v1/ai/interview/rag/search-log`
- 목적: 어떤 히스토리가 검색되었고 어떤 점수로 선택되었는지 확인합니다.

사용자에게 직접 노출할 API는 아니고,
운영자나 개발자가 검색 품질을 점검할 때 도움이 되는 내부용 엔드포인트에 가깝습니다.

## 현재 FastAPI 구조에서의 구현 위치

현재 코드 기준으로는 아래처럼 붙이는 구성이 가장 자연스럽습니다.

- `app/api/v1/endpoints/rag.py`
  히스토리 적재, 삭제, 운영용 재색인처럼 RAG 관리용 라우터를 분리합니다.
- `app/api/v1/schemas/rag.py`
  색인, 삭제, 재색인 요청/응답 스키마를 정의합니다.
- `app/services/rag_service.py`
  임베딩 호출, Qdrant 저장, 검색, 삭제, 포맷팅을 서비스 레이어에서 처리합니다.
- `app/api/v1/endpoints/interview.py`
  기존 `pipeline` 엔드포인트가 텍스트 입력 기반 RAG 검색까지 수행할 수 있도록 확장합니다.
- `app/api/v1/api.py`
  `rag_router`를 `/interview/rag` prefix로 연결합니다.

현재 `interview_service.py`가 생성 로직을 담당하고 있으므로,
RAG도 같은 방식으로 엔드포인트는 얇게 두고 실제 로직은 서비스 레이어로 내리는 편이 일관됩니다.
특히 검색 자체는 외부 API보다 `rag_service.py` 내부 함수로 두고,
`interview_service.py` 또는 파이프라인 서비스가 그것을 호출하는 구조가 가장 자연스럽습니다.

## 권장 우선순위

실제로는 아래 순서로 붙이는 것이 가장 현실적입니다.

1. `POST /api/v1/ai/interview/rag/index`
   인터뷰 종료 후 적재
2. `DELETE /api/v1/ai/interview/rag/index/{history_id}`
   삭제 동기화
3. `POST /api/v1/ai/interview/pipeline`
   내부 RAG 검색 기반 파이프라인 확장
4. `POST /api/v1/ai/interview/rag/reindex`
   운영용 재색인

## 이 테스트를 통해 읽히는 결론

이 실험의 요점은 거창한 지식 검색이 아닙니다.
짧은 인터뷰 아카이브 안에서도, 지금의 문답과 결이 닮은 이전 장면을 다시 붙여 주면 LLM은 더 자연스러운 편집 방향을 얻을 수 있다는 점을 확인하는 테스트입니다.

즉, 이 디렉터리의 RAG는 "정답 검색기"보다는 "이전 인터뷰의 문맥을 다시 불러오는 리서치 어시스턴트"에 가깝습니다.
